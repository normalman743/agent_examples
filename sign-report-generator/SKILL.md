# sign-report-generator

生成 / 检查金融机构请示、签报类公文（.docx）。两个脚本：
`scripts/generate_from_json.py` 读数据 JSON 生成 docx，
`scripts/check_format.py` 读一份已有 docx 核对排版、或通读全文。排版规则
对照 `references/format-standard.md`，数值写在
`references/format-rules-2026.json`，不写死在代码里。

## 三个功能

| 功能 | 干什么 | 定位 |
|---|---|---|
| 功能一 采购立项 | 套现成模板生成采购签报 | 常走，自动化最高（目前只有一般采购-单一来源，后续会加更多模板）|
| 功能二 检查已有 docx | 读别人/旧版的 docx，查合规，按需重建 | 常走 |
| 功能三 通用请示 | 没现成模板时，读或生成任意请示 | 兜底，靠写作指南不靠固定模板 |

模板套不上（不是一般采购-单一来源、或暂时没有对应模板）就走功能三。

## 两个阶段（三个功能都走这两步）

- **一阶段·排版（客观）**：对照 `references/format-standard.md`，用
  `scripts/check_format.py` 自动核对字体/字号/加粗/对齐/缩进/行距/页边距。
  能机械判定对错，**对不上的直接改，不用跟用户商量**。
- **二阶段·内容（判断）**：对照 `references/writing-guide.md` 等，打磨措辞、
  取舍内容、组织结构。这些要人脑判断，**先把打算改什么列清楚 → 跟用户
  商量 → 再动手**，不要自己拍板改业务内容或编造话术。
  - 力度随功能变：功能一**轻**（模板已经兜住措辞，只挑明显不对的）、
    功能二**中**（审别人写的内容）、功能三**重**（没模板兜底，使劲打磨）。

一条统一规则贯穿两阶段：**能机械判定对错的 → 直接改；任何要人脑判断的
→ 列出来商量、不自己猜。** 注意一阶段里也有一小撮 `check_format.py`
判断不了、只能标 ⚠️ 的项（标题梯形/菱形、数字年份跨行断开、附件封面页、
半角标点），这几项虽然属于"排版"，但同样归到"要商量"这一档，不当成
自动通过。

## 该看哪个文件（按场景）

- **排版**（字体/字号/加粗/缩进/行距/页边距）→ `format-standard.md`（权威
  原文）+ `format-rules-2026.json`（脚本用的数值）+ `scripts/check_format.py`
  （自动核对）。别去 `writing-*` / `quality-*` 那些内容文件里找排版规则，
  那里面的格式清单是冗余的，容易跟这三份对不上。
- **内容措辞**（怎么写得准确/平实/简明/庄重、常见错误怎么改）→ 先看
  `writing-guide.md`（已经按请示这一种文种精简过）；不够细再看原文，哪份
  原文的哪一节相关、哪些能跳过，见 `writing-guide.md` 末尾的"原文导航"
  一节，不用每次通读那几份大文件。
- **例子/模板**→ `document-templates.md` 的"请示模板"一节（完整范文），
  或 `template-general-sole-source.json`（结构化、可直接改的单一来源范文）。

## 运行脚本

只需要 `python-docx`：

```
你的python环境 scripts/generate_from_json.py references/template-general-sole-source.json
你的python环境 scripts/check_format.py 某个文件.docx
```

`你的python环境` 换成你机器上实际能用的 Python 调用方式（比如
`conda run -n base python`、`python3`、某个 venv 里的 `python`），每台机器
不一样，不写死。生成的 docx 默认存到输入 JSON 同目录，文件名取自 `title`
加 `_AI草稿` 后缀（提醒收到文件的人这是脚本生成的草稿、需要过一遍，不是
定稿）；也可以用 `out_path` 字段指定完整输出路径（这种情况按你给的路径
原样输出，不加后缀）。`generate_from_json.py` 生成完会自动跑一遍
`check_format.py` 并打印报告（就是一阶段核对），不用再手动多跑一次。

`recipient`（主送单位）、`dept`/`date`（落款）缺失时只会打印警告、留空，
不会有隐藏默认值替你填——这些是内容不是排版规则，必须自己写清楚。

## 功能一：采购立项（套模板生成）

手头是一笔采购、要出立项签报，且类型有现成模板（目前只有
**一般采购-单一来源**）：

1. 读 `references/template-general-sole-source.json`，理解这类签报有哪些
   章节、每段大概怎么措辞、附件怎么组织。**它是参考范文，不是填空表单**，
   也不要直接改它——它是给下一次、下一个人看的原貌，改了就不再是"一般
   采购-单一来源"的范文原貌了。
2. **写之前先吃透材料（收集 → 确认齐全 → 找侧重点）。** 签报的实质内容
   来自附件材料，不是模板套话，所以动笔前：
   - 让用户把这笔采购的附件都传上来并**确认传齐**。对照那约 15 项一般性
     必要文件，缺哪个专门问一句"是这次不需要，还是漏传了"——它们很少缺、
     缺了往往是信号；再问有没有这笔采购特有的特异文件。
   - 读一遍这些材料（docx 用 `check_format.py --read-all`，pdf 直接读；
     暂时读不了的格式请用户口述要点，不硬猜），搞清这笔采购到底在干什么。
   - 提炼**侧重点**——这笔采购该突出什么（单一来源为什么成立、为什么是
     这家、预算/急迫性/风险在哪）。把抓到的重点讲给用户、对齐了再往下写，
     别闷头写完才发现重点抓错。
   - 确认齐全的这套附件就是 JSON 的 `attachments` 数组（实际存在的那部分，
     不是模板固定 15 项）；正文 `{{附件:名称}}` 只能引用真实存在的，缺的
     不能引。
3. 基于上一步的分析，按这笔采购的实际信息**新建一个独立的数据 JSON 文件**
   （字段写法见下面"数据 JSON 怎么写"）。内容适用就照模板写；章节要增减
   （加/拆/合某个 section、改附件数量）之前，先跟用户说清楚加减什么、为什么，
   确认了再动手——结构性判断由用户定，不要自己拍板"这里该加一段"。
4. 跑 `generate_from_json.py` 生成 docx，它会自动跑一遍 `check_format.py`。
5. **一阶段**：看检查报告，❌ 的直接改数据 JSON、重新生成（不要手改 docx）。
6. **二阶段（轻）**：模板已经兜住了措辞，这里只对照 `writing-guide.md` 扫
   一遍，挑明显不对的地方；拿不准的、涉及业务话术的（单一来源认定依据、
   称呼等）列出来问用户，不自己编。
7. 一阶段全过、二阶段没大问题就交付。

类型不是一般采购-单一来源、或暂时没有对应模板 → 走**功能三**。

## 功能二：检查已有 docx（审查 + 按需重建）

拿到一份已有的、不是这个 skill 生成的 docx（别人手写的、旧版本的签报），
要检查合规、或重新整理成合规版本：

1. 先 `scripts/check_format.py <文件.docx> --read-all` 通读全部内容（含
   表格），再跑一遍不带 `--read-all` 的检查报告，搞清楚这份文档现在什么样、
   哪里不合规。
2. **不要直接手改这份 docx**——docx 应该永远是 JSON 生成的派生物，不是可
   编辑的源文件。正确做法是参考 `template-general-sole-source.json` 的结构，
   把读到的内容整理成一份新的数据 JSON，再用 `generate_from_json.py` 重生成。
3. **一阶段**：检查报告里 ❌（字体/字号/加粗/缩进/行距这类跟
   `format-standard.md`/`format-rules-2026.json` 对不上的）是客观错，直接改
   数据 JSON、重新生成，不用商量。
4. **二阶段（中）**：⚠️ 需人工确认的那些，加上内容取舍、结构怎么组织这类
   判断——先按一阶段把能直接改对的改好、生成一版，同时把要判断的部分列
   清楚告诉用户，问怎么处理，不要自己猜一个答案当"最终版"。
5. **读的时候还要专门看有没有超出生成能力的部分**：如果原文有 JSON schema
   现在装不下的东西（表格出现在 `sections`/`table` 覆盖不到的位置、独立的
   附件封面页、结构比 `sections`/`children` 能表达的更复杂）——**不要硬塞、
   不要自己编一种写法凑合**，先说明这部分现在做不到，跟用户商量怎么办。
6. **生成完必须提醒用户**：这份 docx 是读取、理解原文档后重新整理生成的，
   不是对原文档做局部微调，内容取舍和理解上可能有遗漏或偏差，一定要对照
   原文档逐段核对，不能直接当定稿。

目前没有"docx→JSON 自动提取"工具，第 1、2 步靠人/模型读 `--read-all` 的
输出手动整理，不是自动化转换。

## 功能三：通用请示（没有现成模板，读 / 生成）

手头要写/改的是一份请示，但**不是一般采购-单一来源这个现成模板能套的**
（别的采购类型、或别的事务性请示），也就是没有模板兜底：

1. **先吃透材料再动笔**（同功能一那步：收集 → 确认齐全 → 找侧重点）——
   没有模板兜底，更要先读透用户给的材料、跟他对齐这份请示的侧重点，
   否则容易写空。
2. 参考 `template-general-sole-source.json` 的**结构**（有哪些字段、章节怎么
   嵌套、附件怎么组织），但内容全靠 `writing-guide.md` + 需要时查原文（见
   `writing-guide.md` 末尾的原文导航），从零起草数据 JSON。
3. 跑 `generate_from_json.py` 生成 + 自动检查。
4. **一阶段**：跟功能一一样，❌ 直接改。
5. **二阶段（重，使劲）**：没有模板兜底，措辞质量全靠这一步。对照
   `writing-guide.md`（准确/平实/简明/庄重、常见错误改法、标题检查点），
   要更深就查 `writing-techniques.md`/`document-templates.md`/
   `quality-checklist.md` 的相关章节。**把打算怎么写/怎么改列清楚、跟用户
   商量后再定**——尤其涉及真实业务话术、认定依据、称呼这类，必须用户提供，
   不能自己编。
6. 读一份陌生请示同样用功能二的 `--read-all` + 检查 +"先说明超出能力的
   部分"那套流程。

## 数据 JSON 怎么写（功能一、三共用）

**JSON 里所有会出现在正文里的内容都必须是中文**（`title`/`intro`/
`content`/`attachments`/`dept` 等）——这是中文公文，不要写英文
句子或中英混杂的表述。占位符例外：`XXX`/`XXXX` 这类英文字母占位符是留给
业务填真实中文内容用的，不是要你翻译成英文，也不是文档正文本身该出现的文字。

| 字段 | 类型 | 说明 |
|---|---|---|
| `title` | 数组 | 标题，每个元素是居中的一行；留空整段不出现；怎么分行见下 |
| `recipient` | string | 主送单位，比如"公司领导："；不填就空白，不会有默认值 |
| `intro` | 数组 | 主送单位后、第一个章节前的一段开场白，每个元素是独立一段 |
| `sections` | 数组 | 文档主体，见下 |
| `attachments` | 字符串数组，可选 | 附件列表，自动编号+对齐，见下 |
| `dept` / `date` | string | 落款部门/日期，右对齐 |
| `format_config` | string，可选 | 指到别的排版规则 JSON（默认用 `format-rules-2026.json`）|
| `out_path` | string，可选 | 指定输出路径 |

### sections（文档大纲）

```json
{
  "sections": [
    {
      "title": "项目背景",
      "content": ["第一段。", "第二段。"],
      "table": {"headers": [...], "rows": [[...]]},
      "children": [
        {"title": "采购方式", "content": ["..."]},
        {"title": "项目预算", "content": ["..."], "children": [
          {"title": "细分项", "content": ["..."]}
        ]}
      ]
    },
    {"title": "请示事项", "content": ["第一条请示内容。", "第二条请示内容。", "妥否，请批示。"]}
  ]
}
```

- 每个 section 自动编号：顶层"一、二、三..."，`children` 里再嵌一层是
  "（一）（二）（三）..."，再嵌一层是"1.2.3."，再嵌一层是"（1）（2）（3）"。
  四级字体规则对照 format-standard.md：一级黑体不加粗、二级楷体加粗、
  三级仿宋加粗、四级仿宋不加粗。可以嵌任意深度，超过4级沿用4级样式。
- `content` 是数组，每个元素独立成一个 Word 段落——想要几段就写几个
  元素，不用在一个字符串里拼接、数换行符。**分段按"一段一意"**：一段讲清
  一件事，讲完换段；并列的几点改用分条（手写"一是…二是…"或拆成带编号的
  `children`），别把一个意思切成碎句、也别把好几件事挤成一堵墙（更多见
  `writing-guide.md`）。上面例子里"妥否，请批示。"就是这么处理的：它不属于
  任何请示条目，只是数组里最后一个独立段落，没有编号前缀。
- `table` 可选，紧跟在 `content` 后面渲染一张表格（表头加粗居中+底纹，
  单线边框，见下）。
- `title` 都可以省略（渲染空字符串），但通常没有意义。
- 没有自动的"一是/二是"编号机制——如果要这种编号，直接在 `content` 数组
  的每一项里手写前缀（`"一是……"`、`"二是……"`）。

### 标题怎么分行（梯形/菱形排版）

`title` 是数组，每个元素是居中的一行。`format-standard.md` 要求标题多行时
排成**梯形或菱形**，禁止矩形（每行等长）和沙漏形（上下长中间短）：

- 分两行：**上短下长**或**下短上长**（选一种，都算梯形）
- 分三行：从上到下递减的**倒梯形**、递增的**正梯形**，或**上下短中间长**
  的菱形
- 回行**不能拆开**词组、人名、地名、单位名称等专有名词
- 整体要"词意完整、排列对称、长短适宜、间距恰当"

这些判断需要理解中文语义边界，脚本不会自动算，需要写 JSON 的人（或
调用这个 skill 的模型）自己决定怎么分行。按下面的方法判断：

1. 先看标题总字数是否超过一行大约能放的字符数（按标题字号/页面宽度
   估算，当前配置约 20 字/行——`format-rules-2026.json` 改了字号/页边距，
   这个数会变）。没超过就整个标题作为 `title` 数组里唯一一个元素，不分行。
2. 超过了，就要分 2-4 行（超过 4 行脚本会警告，说明标题该精简了）。先算
   "总字数 ÷ 计划行数"得到一个大致的每行字数，再在这个字数附近的
   词组/专有名词边界上找断点——不能从中间劈开一个词，宁可某一行多/少
   一两个字，也要保证"词意完整"。
3. 按上面"梯形/菱形"的形状规则挑一种排布（两行选上短下长或下短上长；
   三行选递增/递减/菱形），检查每行长度是否明显不对称、有没有出现矩形
   （每行几乎等长）或沙漏形（两头长中间短）——这两种是明确禁止的形状。
4. 如果无论怎么分都避不开"某一行短得突兀"（比如只剩 1-2 个字单独一行）
   或者要分到 5 行以上才能避免拆词，说明标题本身太长了，应该跟催办人
   商量精简标题内容，而不是勉强凑一个难看的分行。

脚本只做两个粗略的安全网检查（不是精确排版引擎，只是警戒线），分行判断
本身还是要靠上面的人工/模型推理：
- 单行不分行、且字数超过一行大约能放的字符数：打印警告。
- 分了行、但超过 4 行：打印警告，建议精简标题内容。

### 表格

任意 section 都可以带 `table`：

```json
{
  "title": "采购需求",
  "content": "需求部门及品类如下表所示：",
  "table": {
    "headers": ["产品大类", "产品明细", "需求部门"],
    "rows": [
      ["办公耗材", "打印纸、墨盒", "运营部、财务部"],
      ["办公文具", "笔、本、文件夹", "全部成员单位"]
    ]
  }
}
```

样式固定：单线黑框、表头加粗居中+浅灰底纹、内容居中、字号比正文小一号
（12pt，即小四号）。**`format-standard.md` 完全没有规定表格样式**，这是我们
自己定的，想改边框粗细/底纹颜色/字号，改 `references/format-rules-2026.json`
里的 `table` 那一节。

### 附件（自动编号+对齐）

一般采购-单一来源的 `attachments` 通常分两类：一类是**一般性必要文件**
（大约 15 项，基本每次都有、很少缺），另一类是**特异文件**（随这笔采购的
具体情况变，不固定）。具体清单以公司内部的最终模板为准（见下面"业务内容
覆盖范围"里关于模板的说明）。

`attachments` 是字符串列表，用真正的 Word 换行（`<w:br/>`）分隔多条内容，
不是塞一堆 `\n`——`\n` 在 docx 的 `<w:t>` 里不会被 Word 当换行显示，必须用
`run.add_break()` 生成真正的 `<w:br/>` 才行。所有续行悬挂缩进对齐到
"附件："后面的文字位置。

超过 9 条时（到 10、11...），1-9 编号后面补一个空格，让文字大致跟两位数
编号对齐：

```
附件： 1． 效能分析报告
      2． 需求说明书
      ...
      10．合同草案
      11．合同审查流程
```

对齐效果在不同平台上可能有细微出入，生成后建议在目标平台上肉眼确认一下。
超过 99 条（三位数编号）会直接报错退出，不会硬凑一个明显错位的对齐效果。

#### 正文里引用附件：按名字引用，别手写编号

正文（`content`/`intro`）里引用附件时，不要手写"附件3"这种固定编号——编号
是脚本按**正文里第一次引用的先后**自动算的，手写的数字一旦和实际引用顺序
或附件增删对不上就会错位。改用按名字引用：

```json
{
  "attachments": ["需求说明书", "市场调研报告", "合同草案"],
  "sections": [
    {"title": "x", "content": "先说市场调研报告（{{附件:市场调研报告}}），再说需求说明书（{{附件:需求说明书}}）。"}
  ]
}
```

- **编号按实际引用顺序，不按 `attachments` 数组顺序。** 上面正文先引用"市场
  调研报告"、后引用"需求说明书"，所以"市场调研报告"是"附件1"、"需求说明书"
  是"附件2"，跟它们在 `attachments` 数组里的位置无关。底部附件说明列表也按
  这个顺序重排，保证正文里的"附件N"和列表第 N 条对得上——`attachments` 数组
  只负责**声明有哪些附件、每条的准确名字**，顺序随便写。
- 括号自己写在 `content` 里（marker 只产出裸文本"附件N"，不带括号）。
- `名称` 必须和 `attachments` 里某一项完全一致（含标点）。两类对不上仍然正常
  生成，但会 print 警告：正文引用了、`attachments` 没声明的（打错/漏填）→
  原样保留标记不编号；`attachments` 声明了、正文从没引用的 → 仍列进附件说明、
  接在被引用的之后编号，提醒确认是不是漏引了（正常每条附件都会在正文引用一次）。

## 排版规则配置（format-rules-2026.json）

字体、字号、加粗、行距、缩进、页边距这些数值都在 `references/format-rules-2026.json`
里，不是硬编码在 `generate_from_json.py` 里。以后排版新规改了：
改这个文件里的数值，或者复制一份新文件（比如 `format-rules-2027.json`），
在数据 JSON 里用 `format_config` 字段指过去，不用改脚本代码。

这份规则是 2026.6 生效、目前在用的版本，停用时间待定——以后新规替换掉它时，
按上面说的复制新文件的方式处理，不要直接改这份文件（除非确认 2026.6 版本
已经停用）。

**这个文件只装标准规定的排版规则，不装任何默认内容文字**（比如"公司领导："
这种称呼，或者"妥否，请批示。"这种收尾的一句话）——那些是业务约定不是排版
标准，必须由数据 JSON 自己写清楚，脚本不会替你填。

### 只支持四款字体，不做变体识别

`font` 字段是精确匹配的字符串，只认这四个：`方正小标宋简体`（标题/附件
标题）、`黑体`（一级序号）、`楷体`（二级序号）、`仿宋_GB2312`（正文/
主送单位/三四级序号/附件说明/落款/表格）。这几款字体各自还有其他叫法
（比如仿宋_GB2312 也可以叫方正仿宋_GBK、FangSong），国标层面都合规，
但这个 skill 不做等效变体识别——`check_format.py` 核对时字体名对不上
这四个之一就会报不合格，即使实际用的是等效变体也一样，不算例外。

## check_format.py 详解（一阶段核对）

```
你的python环境 scripts/check_format.py 生成的文件.docx
```

对照 `references/format-standard.md` 的"排版检查要点"逐条核对，判断标准
读的是 `references/format-rules-2026.json`（跟生成用的是同一份配置，两边
不会对不上）。每条输出三种结果之一：

- ✅ **能自动核对且通过**：字体、字号、加粗、对齐、缩进、行距这些 python-docx
  能从文件里直接读到数值的地方。
- ❌ **能自动核对但没通过**：报具体是哪一段、实际值是什么、应该是什么。
- ⚠️ **需人工确认**：`format-standard.md` 明确要求、但 docx 文件本身不存
  判断所需信息的两类，脚本不会猜、不会冒充自动验证过：
  1. **标题多行是否符合梯形/菱形**（词意断得对不对、排列对不对称）——
     docx 只能告诉你有几行、每行几个字，"好不好看"要人/模型看着文字判断。
  2. **正文回行是否拆开了数字/年份**——这取决于 Word 实际怎么排版换行，
     docx 文件里根本没存这个信息，必须打开 Word/WPS 实际看。
  3. **"六、附件"独立封面页是否存在**——`generate_from_json.py` 没实现
     这个要素（见下面"已知限制"），这条固定会被标成需人工确认。
  4. **半角标点混入中文正文**——这条脚本会扫，但只在半角标点紧挨着中文
     字符时才报（纯数字/字母之间的半角标点，比如日期、时间、编号，不算
     问题），是启发式规则不是精确解析，报出来的地方自己看一眼再改，
     可能有个别误判，所以也标成需人工确认而不是直接判定失败。

这四项 ⚠️ 就是"一阶段"里机器判断不了、要归到"跟用户商量"那一档的部分。

想看更细的原始数据（比如自己判断标题该怎么分行更好看），加 `--dump`，
会把每段的对齐/缩进/行距/字体字号原样打印出来。

想单纯通读一份 docx 的全部文字内容（不带格式属性），加 `--read-all`——
按文档实际顺序打印段落和表格。**这个跟机械检查用的段落列表不是一回事**：
检查逻辑只看 `doc.paragraphs`，python-docx 这个属性不会遍历表格单元格里
嵌套的内容，表格文字完全看不到；`--read-all` 直接走文档 XML 顺序，段落
和表格都不漏，才是真正"读到全部内容"。看一份陌生的、可能带表格的 docx
时用这个，不要只看 `--dump`。

如果检查出 ❌，**改数据 JSON、重新跑 `generate_from_json.py`，不要直接
手改生成出来的 docx**——不然下次同一份 JSON 再生成一次，手改的内容就
没了，等于没改。

## 已知限制（对照 format-standard.md 逐条核对，未覆盖或做不到的部分）

以下几点是 `format-standard.md` 明确要求、但当前脚本**做不到**或**没做**的：

1. **标题梯形/菱形的具体断行位置**——脚本只提供手动 `\n` 分行+字数警告，
   不会自动判断"在哪断词意才完整、长短怎么排才对称"，这需要人工判断。
2. **正文回行不能拆开数字/年份**——纯 Word 自动换行落点，脚本没有做任何
   "不间断"处理，长数字/日期正好卡在行尾会被硬拆开，需要人工检查。
3. **"结构层次只有两层时用'一、'+'1.'"（跳过"（一）"这一层）**——现在
   `sections`/`children` 的层级是严格由嵌套深度决定的，没有字段能让某个
   section 强制"跳级"。
4. **"六、附件"（附件封面页：独立成页的"附件1"标签+居中标题）**——完全
   没实现。脚本只做了"五、附件说明"（正文里"附件：1.xxx"那一段）。

以下几点**不是** `format-standard.md` 的要求，是脚本自己的假设/外延，
不要误认为是标准规定：
- "妥否，请批示。"这类收尾句、`recipient`（主送单位）没有默认文字，标准
  也没规定该写什么，纯粹是业务内容，由数据 JSON 自己写在 `content` 里，
  不是脚本里某个专门字段/格式。
- 表格样式（边框/底纹/字号）——标准完全没提表格。
- 附件 1-9 与 10+ 编号之间要不要对齐——标准只提了单条回行首字对齐，多条
  不同位数之间怎么对齐是我们自己加的外延，不是标准原文逐字规定（见上面
  "附件"一节）。

## 业务内容覆盖范围

- 已跑通并验证的类型：**一般采购-单一来源**（用
  `references/template-general-sole-source.json` 这份示例验证的生成/检查流程）。
- 还没做（等业务范文/规则）：一般采购-多来源、集中采购-竞标、集中采购-单一来源。
  这些将来会作为功能一新增的模板陆续补进 `references/`；在补进来之前，遇到
  这些类型走功能三（通用请示）从零起草。
- **`references/template-general-sole-source.json` 是示意用的参考结构，不是
  最终定稿**——真正的最终版（含完整、确定的附件清单等）属于半设计机密，在
  Windows 环境单独维护，不放进这个仓库。所以这里的模板：章节结构和写法可以
  参考，但**附件清单、具体条款措辞不要当权威定稿**，实际使用以公司内部的
  最终模板为准。
- 模板里标了 `XXX：单一来源认定依据条款` 的地方是占位提示，不是真实业务
  话术——实际使用前必须把公司《一般采购管理办法》里单一来源认定的具体条款
  文字填进去。
